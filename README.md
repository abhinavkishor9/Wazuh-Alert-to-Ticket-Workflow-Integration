# Wazuh Alert-to-Ticket Workflow Integration

## Overview

This lab demonstrates how security alerts generated by Wazuh can be forwarded to a ticketing endpoint and converted into structured incident records.

A custom Wazuh integration was implemented using Python. The integration processes selected JSON alerts, extracts relevant detection and endpoint information, maps the Wazuh rule level to a ticket priority, and submits the resulting payload to a local REST API.

A lightweight Python-based mock ticket API was created to receive the requests and store ticket records as JSON files. This allowed the complete alert-to-ticket workflow to be tested without depending on an external ITSM platform.

The integration was successfully executed, and a ticket was created from a Wazuh Rule ID 533 alert.

## Lab Objectives

- Understand how Wazuh integrations connect security monitoring with incident tracking.
- Examine the Wazuh Integrator component and its role in forwarding selected alerts.
- Identify suitable alerts and configure rule-based integration filtering.
- Develop a custom Python integration script to process Wazuh JSON alerts.
- Extract alert, rule, timestamp, and agent information.
- Map Wazuh alert severity to a ticket priority.
- Create a local mock REST API to receive ticket payloads.
- Configure Wazuh to invoke the custom integration.
- Validate API availability, integration execution, and ticket creation.
- Compare generated ticket information with the original Wazuh alert.
- Identify integration limitations and distinguish successful ticket creation from confirmed incident classification.

## Workflow Architecture

The implementation follows this sequence:

1. A monitored endpoint or the Wazuh Manager generates an event.
2. Wazuh processes the event and generates a security alert.
3. The Integrator evaluates the configured alert filters.
4. The custom integration script receives the matching alert JSON.
5. The script extracts relevant fields and constructs a ticket payload.
6. The integration submits the payload to the local mock ticket API.
7. The API creates a JSON ticket record and returns a response.
8. The ticket is inspected and compared against the original Wazuh alert.

## Implementation

### 1. Alert Identification

The following alert file was inspected:

`/var/ossec/logs/alerts/alerts.json`

The review identified multiple Windows endpoint events, including Rule ID 597 registry key deletion alerts, as well as a Manager-generated Rule ID 533 alert.

The integration was configured to filter for Rule ID 533.

### 2. Local Mock Ticket API

A Python HTTP server was created at:

`/opt/wazuh-ticket-lab/mock_ticket_api.py`

The service listened on:

`127.0.0.1:5000`

It provided two endpoints:

- `GET /health` — returns the API health status.
- `POST /tickets` — accepts a JSON payload and creates a ticket record.

Ticket records were stored under:

`/opt/wazuh-ticket-lab/tickets/`

### 3. Custom Integration Script

The custom integration script was created at:

`/var/ossec/integrations/custom-ticket`

Its responsibilities included:

- Reading the alert JSON passed by Wazuh.
- Extracting the alert ID and timestamp.
- Extracting rule ID, level, description, and groups.
- Extracting agent ID, name, and IP address.
- Mapping the rule level to a ticket priority.
- Constructing a structured JSON payload.
- Submitting the payload to the configured ticket API.
- Reporting HTTP and connection errors.

The script used the following lab priority mapping:

| Wazuh Rule Level | Ticket Priority |
|---|---|
| 14 and above | Critical |
| 12–13 | High |
| 7–11 | Medium |
| Below 7 | Low |

This mapping was defined for the lab and should not be treated as a universal SOC severity policy.

### 4. Wazuh Integration Configuration

The Manager configuration was backed up before modification:

`/var/ossec/etc/ossec.conf.pre-lab124`

The custom integration was configured with:

- Integration name: `custom-ticket`
- Ticket endpoint: `http://127.0.0.1:5000/tickets`
- Rule filter: `533`
- Alert format: `json`

The configuration passed XML syntax validation, and the Wazuh Manager restarted successfully.

The Wazuh Integrator process was subsequently reported as running.

## Key Findings and Limitations

- The Wazuh Integrator was initially not running because no remote integration was configured.
- After adding the custom integration and restarting the Manager, the Integrator process started and enabled `custom-ticket`.
- The mock API was accessible only through the local loopback address.
- The successful ticket originated from `localhost.localdomain`, not the Windows endpoint.
- Windows Rule ID 597 alerts were visible in the recent alert output, but they were not the selected Rule ID 533 integration target.
- HTTP 201 and the resulting ticket record confirmed successful ticket submission and creation.
- Duplicate-submission behavior was not independently validated.
- No external ITSM platform was connected.

## Final Assessment

The alert-to-ticket workflow was successfully implemented and validated using a local mock API.

A Wazuh Rule ID 533 alert was processed by the custom integration, transmitted to the ticket receiver, and stored as a structured ticket with status `NEW`.

The exercise demonstrates the technical workflow required to connect Wazuh detections with incident tracking. It does not establish a production ITSM integration, automatic analyst assignment, or complete incident lifecycle management.

## Scope and Safety

This implementation is intended for a controlled lab environment.

- The mock receiver listens only on `127.0.0.1`.
- The API is not configured with production authentication.
- The API key value used in the local lab is a placeholder.
- Production integrations must use authenticated HTTPS endpoints.
- Sensitive alert contents, credentials, API tokens, and private configuration values must not be committed to GitHub.
- Ticket creation should not be interpreted as confirmation of malicious activity or compromise.
