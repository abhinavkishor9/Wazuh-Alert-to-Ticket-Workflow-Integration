# Wazuh-Alert-to-Ticket-Workflow-Integration
## Overview
A Wazuh alert-to-ticket workflow connects security monitoring with incident management by converting selected security alerts into structured, trackable tickets.

When Wazuh detects an event that matches a configured detection rule, it generates an alert containing information such as the rule ID, severity level, timestamp, agent details, and event description. Instead of relying entirely on analysts to manually record every relevant alert, Wazuh can forward selected alerts to an external application through its integration framework.

A custom integration can process the alert, extract the required information, construct a structured payload, and submit it to a ticketing system through an API.

### Key Components

- **Wazuh Manager:** Processes security events, evaluates detection rules, and generates alerts.
- **Wazuh Integrator:** Identifies alerts matching the configured integration criteria and invokes the corresponding integration script.
- **Custom Integration Script:** Processes the alert JSON, extracts relevant fields, maps alert information into ticket attributes, and sends the payload to the configured endpoint.
- **Ticketing API:** Receives the submitted payload and creates an incident or ticket record.
- **SOC Analyst:** Reviews the ticket, validates the alert, performs investigation, documents findings, and tracks the response.

### How the Workflow Operates

1. **Event Detection:** An endpoint or the Wazuh Manager generates an event.
2. **Alert Generation:** Wazuh processes the event and generates an alert when a detection rule matches.
3. **Alert Filtering:** The Integrator selects alerts based on configured conditions, such as rule ID, rule level, or rule group.
4. **Alert Processing:** The custom integration script reads the alert JSON and extracts relevant information.
5. **Payload Construction:** Extracted details are organized into a structured ticket payload.
6. **API Submission:** The integration sends the payload to the configured ticketing endpoint.
7. **Ticket Creation:** The receiving application processes the request and creates a ticket.
8. **Investigation and Tracking:** The SOC analyst reviews the ticket, investigates the evidence, and updates its status.

### Information Included in a Ticket

| Field | Purpose |
|---|---|
| Ticket ID | Unique reference for the created ticket |
| Alert ID | Identifies the original Wazuh alert |
| Summary | Provides a brief description of the detection |
| Rule ID | Identifies the Wazuh detection rule |
| Rule Level | Represents the severity level assigned by Wazuh |
| Agent Details | Identifies the endpoint or Manager that generated the alert |
| Timestamp | Records when the alert occurred |
| Rule Groups | Provides detection classification |
| Priority | Represents the ticket priority based on the configured mapping |
| Status | Tracks the ticket's current state |

### Why Alert-to-Ticket Integration Matters

In a SOC environment, security alerts need to be reviewed, prioritized, assigned, and tracked. Manually transferring relevant alert information into an incident management platform can introduce delays and inconsistent documentation.

Automating this process helps:

- Reduce manual alert documentation.
- Improve incident tracking and accountability.
- Preserve important detection details for investigation.
- Support consistent alert prioritization.
- Maintain a record of security events requiring analyst attention.
- Provide a foundation for integration with incident response platforms.

### Important Distinction

A Wazuh alert represents a detection generated by a security rule. A ticket represents a record created to track review or investigation of that detection. Ticket creation does not automatically confirm malicious activity, compromise, or a security incident.

The integration must also be configured carefully to avoid forwarding unnecessary alerts or creating duplicate tickets. Alert filtering, payload validation, error handling, and ticket correlation are important parts of a reliable workflow.

A local mock API can demonstrate the alert-to-ticket mechanism in a controlled lab environment. A production implementation requires integration with an actual ticketing platform, appropriate authentication, secure communication, and a defined incident management process.

This lab demonstrates how security alerts generated by Wazuh can be forwarded to a ticketing endpoint and converted into structured incident records.

A custom Wazuh integration was implemented using Python. The integration processes selected JSON alerts, extracts relevant detection and endpoint information, maps the Wazuh rule level to a ticket priority, and submits the resulting payload to a local REST API.

A lightweight Python-based mock ticket API was created to receive the requests and store ticket records as JSON files. This allowed the complete alert-to-ticket workflow to be tested without depending on an external ITSM platform.

The integration was successfully executed, and a ticket was created from a Wazuh Rule ID 533 alert.

## Lab Objectives

The objectives of this lab are to:

- Understand how security monitoring alerts can be connected to an incident tracking workflow.
- Examine how Wazuh identifies and forwards alerts that match configured integration criteria.
- Identify relevant alert attributes from Wazuh JSON records for downstream processing.
- Develop a Python-based integration script to transform detection data into a structured ticket payload.
- Implement a local REST API to receive and process ticket creation requests.
- Configure the integration to forward alerts based on a specific Wazuh rule ID.
- Apply a defined mapping between Wazuh rule levels and ticket priorities.
- Establish communication between the Wazuh Integrator and the local ticket receiver.
- Validate the integration through API health checks, service status, execution logs, and HTTP response codes.
- Verify that the generated ticket accurately represents the source alert, including its rule details and agent identity.
- Understand the importance of alert filtering, ticket identification, and duplicate-submission handling.
- Identify potential integration failures involving script execution, permissions, API availability, and payload processing.
- Distinguish successful ticket creation from confirmation of a security incident.
- Evaluate the limitations of a simulated ticketing environment compared with a production ITSM integration.

## Lab Scenario

A SOC environment uses Wazuh 4.13.1 to monitor security events generated by a Windows endpoint and the Linux Manager. As the volume of security alerts increases, manually recording relevant detections in an incident tracking system can become time-consuming and may lead to inconsistent investigation records.

To explore automated incident tracking, a custom alert-to-ticket integration is introduced. The objective is to take a selected Wazuh alert, extract its relevant detection details, convert them into a structured JSON payload, and submit the information to a ticketing endpoint.

The implementation uses a Python-based custom integration script and a locally hosted mock REST API. The integration is configured to process alerts matching Wazuh Rule ID `533`, which detects changes in listened-port status. The script extracts the alert ID, rule details, severity level, timestamp, and agent information before mapping the alert into a ticket format.

The workflow involves several stages:

- **Alert identification:** Examine existing Wazuh JSON alerts and select a suitable detection rule for integration testing.
- **Integration development:** Create a Python script to process matching alerts and construct structured ticket payloads.
- **Ticket API implementation:** Develop a local REST API to receive requests, validate the submitted data, and store ticket records.
- **Wazuh configuration:** Register the custom integration, configure the API endpoint, and apply rule-based filtering.
- **Workflow validation:** Generate a matching alert and verify integration execution, API communication, HTTP response, and ticket creation.
- **Evidence correlation:** Compare the generated ticket with the original Wazuh alert to confirm that the rule information and agent attribution are consistent.

During validation, the integration successfully forwards a Rule ID `533` alert generated by `localhost.localdomain`. The mock API returns HTTP `201`, and a ticket is created with status `NEW` and priority `Medium`.

The investigation also identifies Windows endpoint alerts with Rule ID `597`, describing registry key deletion events. However, these alerts are outside the configured Rule ID `533` filter and are not the source of the generated ticket. This distinction helps establish that successful ticket creation must be evaluated against the original alert rather than assumed to represent every monitored endpoint.

**Scenario objective:** Demonstrate how a selected Wazuh security alert can be automatically converted into a structured incident ticket, validate the communication between the Wazuh Integrator and a ticketing API, and examine the accuracy of the resulting ticket information.

**Scope limitation:** The implementation uses a local mock ticket API rather than a production ITSM platform. It validates alert processing, payload construction, API submission, and ticket creation, but does not demonstrate external platform authentication, analyst assignment, escalation, or complete incident lifecycle management. Ticket creation represents an investigation-tracking action and does not independently confirm malicious activity or system compromise.

## Workflow Architecture

The implementation follows this sequence:

1. A monitored endpoint or the Wazuh Manager generates an event.
2. Wazuh processes the event and generates a security alert.
3. The Integrator evaluates the configured alert filters.
4. The custom integration script receives the matching alert JSON.
5. The script extracts relevant fields and constructs a ticket payload.
6. The integration submits the payload to the local mock ticket API.
7. The API creates a JSON ticket record and returns a response.
8. The ticket is inspected and compared against the original Wazuh alert.

## Implementation

### 1. Alert Identification

The following alert file was inspected:

`/var/ossec/logs/alerts/alerts.json`

The review identified multiple Windows endpoint events, including Rule ID 597 registry key deletion alerts, as well as a Manager-generated Rule ID 533 alert.

The integration was configured to filter for Rule ID 533.

### 2. Local Mock Ticket API

A Python HTTP server was created at:

`/opt/wazuh-ticket-lab/mock_ticket_api.py`

The service listened on:

`127.0.0.1:5000`

It provided two endpoints:

- `GET /health` — returns the API health status.
- `POST /tickets` — accepts a JSON payload and creates a ticket record.

Ticket records were stored under:

`/opt/wazuh-ticket-lab/tickets/`

### 3. Custom Integration Script

The custom integration script was created at:

`/var/ossec/integrations/custom-ticket`

Its responsibilities included:

- Reading the alert JSON passed by Wazuh.
- Extracting the alert ID and timestamp.
- Extracting rule ID, level, description, and groups.
- Extracting agent ID, name, and IP address.
- Mapping the rule level to a ticket priority.
- Constructing a structured JSON payload.
- Submitting the payload to the configured ticket API.
- Reporting HTTP and connection errors.

The script used the following lab priority mapping:

| Wazuh Rule Level | Ticket Priority |
|---|---|
| 14 and above | Critical |
| 12–13 | High |
| 7–11 | Medium |
| Below 7 | Low |

This mapping was defined for the lab and should not be treated as a universal SOC severity policy.

### 4. Wazuh Integration Configuration

The Manager configuration was backed up before modification:

`/var/ossec/etc/ossec.conf.pre-lab124`

The custom integration was configured with:

- Integration name: `custom-ticket`
- Ticket endpoint: `http://127.0.0.1:5000/tickets`
- Rule filter: `533`
- Alert format: `json`

The configuration passed XML syntax validation, and the Wazuh Manager restarted successfully.

The Wazuh Integrator process was subsequently reported as running.

## Key Findings and Limitations

- The Wazuh Integrator was initially not running because no remote integration was configured.
- After adding the custom integration and restarting the Manager, the Integrator process started and enabled `custom-ticket`.
- The mock API was accessible only through the local loopback address.
- The successful ticket originated from `localhost.localdomain`, not the Windows endpoint.
- Windows Rule ID 597 alerts were visible in the recent alert output, but they were not the selected Rule ID 533 integration target.
- HTTP 201 and the resulting ticket record confirmed successful ticket submission and creation.
- Duplicate-submission behavior was not independently validated.
- No external ITSM platform was connected.
